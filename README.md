# Time Tracker

C++20 / Drogon API и PostgreSQL 16 запускаются через Docker Compose.
Тесты запускаются отдельным контейнером с изолированной тестовой БД.
Реализованы регистрация, вход, текущий пользователь, CRUD проектов и задач.
Реализованы таймер (Start/Pause/Resume/Stop), история, ручные интервалы, отчёты.

## Основной запуск: Docker

Нужны Git и Docker Desktop (на Linux — Docker Engine с Compose). Компилятор,
CMake, Python и C++-библиотеки на компьютере для этого варианта не нужны.
Команды выполняются из корня проекта.

На новом компьютере создайте `.env` из `.env.example` и задайте собственные
POSTGRES_PASSWORD и JWT_SECRET (минимум 32 байта). Секрет можно получить
командой `openssl rand -hex 32`. Существующий локальный `.env` уже настроен;
не перезаписывайте его. В Git хранится только пример, а в Docker-образ .env не попадает.

Запустите Docker Desktop, затем:

```sh
docker compose up --build -d --wait
```

Обычный запуск поднимает только db и api. Первая сборка скачивает Linux,
компилятор и зависимости и может занять несколько минут. Локальная папка build
не используется: Docker собирает отдельный Linux-бинарник из исходников.

Проверка:

```sh
docker compose ps
curl -i http://127.0.0.1:8080/health
```

Оба сервиса должны быть healthy. Ожидается HTTP 200 и
`{"database":"ok","status":"ok"}`. Этот запрос проверяет и сервер, и подключение к БД.
В Postman адрес тот же: http://127.0.0.1:8080. Импортируйте коллекцию,
выполните Register или Login, затем запросы проектов, задач и таймера.

```sh
docker compose logs --tail=100 api
docker compose logs -f api
```

Ctrl+C при просмотре logs прекращает просмотр, а контейнер продолжает работать.
Остановка приложения с сохранением БД:

```sh
docker compose stop api db
```

Для последующих запусков после сборки достаточно `docker compose up -d --wait`.
После изменений C++-кода снова выполните команду с `--build`.
Если 8080 занят старым локальным сервером, остановите его Ctrl+C либо измените
BACKEND_PORT в .env (тогда тот же порт укажите в Postman).

Внутри контейнера API слушает 0.0.0.0:8080 и подключается к db:5432.
На компьютере API опубликован только на 127.0.0.1:${BACKEND_PORT:-8080},
а PostgreSQL — на 127.0.0.1:${DB_PORT:-5432}. Значения DB_HOST, DB_PORT и
BACKEND_HOST для API Compose задаёт самостоятельно; host-настройки в .env
остаются пригодны для локального запуска без Docker.
Рабочий том postgres_data сохранён; контейнеризация не очищает пользователей и проекты.

## Тесты в Docker

```sh
docker compose run --rm --build tests
```

При повторном запуске без изменений можно `docker compose run --rm tests`.
Результат PASS и число HTTP-проверок появятся в терминале. Код выхода 0 означает
успех; при ошибке будет traceback и ненулевой код выхода.

Тесты входят в профиль test и не стартуют вместе с обычным приложением.
Compose поднимет отдельный test-db в изолированной внутренней сети. У него нет
опубликованного порта и рабочего тома. Временные данные хранятся в tmpfs.
Контейнер tests использует тот же Linux-бинарник, запускает собственный API на
свободном внутреннем порту и проверяет в том числе его перезапуск. Docker-сокет
внутрь не передаётся. Рабочий API и рабочая БД тестам не нужны и не затрагиваются.

После выполнения --rm удалит контейнер tests. Вспомогательную тестовую БД можно остановить:

```sh
docker compose --profile test stop test-db
```

При необходимости открыть терминал тестового контейнера:

```sh
docker compose run --rm --entrypoint sh tests
```

После остановки/перезапуска test-db временные данные пропадают. Каждый запуск
тестов дополнительно создаёт отдельную БД со случайным именем и удаляет её в конце.

## Альтернативный запуск: API локально на macOS

Если запущен контейнер API, сначала выполните `docker compose stop api`, чтобы освободить порт.

Все команды выполняются из корня проекта. Запустите Docker Desktop.
Зависимости описаны в [backend/DEPENDENCIES.md](backend/DEPENDENCIES.md).

```sh
brew install cmake git libpq jsoncpp openssl@3 libsodium
```

Локальный `.env` уже настроен, секрет JWT сгенерирован. Если на другом компьютере
файла нет, скопируйте `.env.example` в `.env` и замените пароль и JWT_SECRET.
Секрет можно сгенерировать командой `openssl rand -hex 32`.
Файл .env исключён из Git. ALGORITHM=HS256, TOKEN_EXPIRE_HOURS=1.

Сейчас в локальном `.env` DB_PORT=5433, поскольку 5432 занят другой БД.
Backend использует DB_HOST=127.0.0.1. Внутри контейнера порт БД — 5432.

```sh
docker compose up -d --wait db
```

Таблицы users, projects, tasks и time_entries создаются init.sql при первой инициализации пустого тома.
Для уже существующего тома примените скрипт следующей командой. Она создаёт
недостающие таблицы и индекс, не удаляет данные и не меняет существующие колонки:

```sh
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /docker-entrypoint-initdb.d/init.sql'
```

Сборка (первая сборка скачивает Drogon 1.9.11 и jwt-cpp 0.7.1):

```sh
cmake -S backend -B build -U 'OPENSSL_*' -DCMAKE_BUILD_TYPE=Debug \
  -DOPENSSL_ROOT_DIR="$(brew --prefix openssl@3)" \
  -DCMAKE_PREFIX_PATH="$(brew --prefix openssl@3);$(brew --prefix libpq);$(brew --prefix jsoncpp);$(brew --prefix libsodium)"
cmake --build build --parallel 2
```

Запуск в том же терминале (zsh/bash):

```sh
set -a
source .env
set +a
./build/time_tracker_backend
```

Config читает окружение процесса, а не файл .env. При запуске через IDE передайте
эти же переменные в настройках запуска. Source используйте для своего доверенного .env.

Сервер: http://127.0.0.1:8080. Остановка — Ctrl+C.
Из другого терминала: `curl -i http://127.0.0.1:8080/health`.
Остановка БД с сохранением данных: `docker compose stop db`.
Не удаляйте том для повторного применения SQL.

## Postman

Импортируйте [коллекцию](postman/TimeTracker.postman_collection.json).
Запросы расположены в порядке проверки. Register и Login сохраняют access_token
в переменную коллекции, Create project сохраняет project_id.
Запускайте запросы последовательно. Если пользователь уже существует, вместо
Register выполните Login. При повторном запуске Create создаёт новый проект.
Используйте Postman Desktop или Desktop Agent для обращений к localhost.

Для ручных запросов: Body → raw → JSON, Content-Type: application/json.
После входа выберите Authorization → Bearer Token и вставьте access_token.

| Метод | Путь | Результат |
|---|---|---|
| POST | /auth/register | 201, пользователь и access-токен |
| POST | /auth/login | 200, пользователь и access-токен |
| GET | /users/me | 200, текущий пользователь |
| POST | /projects | 201, созданный проект |
| GET | /projects | 200, массив своих проектов |
| GET | /projects/{id} | 200, свой проект |
| PATCH | /projects/{id} | 200, изменённый проект |
| DELETE | /projects/{id} | 204, пустой ответ |

Регистрация (name необязателен, по умолчанию часть email перед @):

```json
{"email":"olesya@example.com","password":"my-password-123","name":"Олеся"}
```

Вход:

```json
{"email":"olesya@example.com","password":"my-password-123"}
```

Ответ регистрации/входа:

```json
{
  "access_token":"<JWT>",
  "token_type":"Bearer",
  "expires_in":3600,
  "user":{"id":"<UUID>","name":"Олеся","email":"olesya@example.com"}
}
```

Создание проекта:

```json
{"name":"Учебный проект"}
```

Редактирование проекта: можно передать одно или оба поля.

```json
{"name":"Новое название","is_completed":true}
```

Проект содержит id, user_id, name, is_completed, created_at (UTC, ISO 8601).
Владельца сервер берёт из проверенного JWT; передавать user_id нельзя.

Ошибки имеют вид `{"error":"..."}`:

- 400 — неверный JSON, поля, UUID, email или длина пароля/названия.
- 401 — неверный пароль, отсутствующий, испорченный или истёкший токен.
- 404 — проект отсутствует или принадлежит другому пользователю.
- 409 — email занят; проект содержит задачи; задача содержит интервалы или её таймер не остановлен.
- 500 — внутренняя ошибка, например недоступна БД или не применён SQL.

## Договорённости

Email проверяется по формату (обычный ASCII-адрес), без письма подтверждения.
Пробелы по краям убираются, адрес приводится к нижнему регистру; уникальность
гарантирует индекс lower(email) в PostgreSQL, включая параллельные регистрации.
Пароль — 8–20 Unicode-кодовых точек, без обрезки пробелов, хранится как Argon2id.
JWT содержит sub (UUID пользователя), iss, iat, exp. Только HS256, без refresh.
После часа нужно войти снова. Logout на клиенте удаляет токен; серверного отзыва нет.

SQL описывает все четыре таблицы. is_paused хранится в tasks (bool, default false).
На задачу может приходиться несколько time_entries. Удаление физическое:
проект с задачами и задачу с интервалами удалить нельзя (409, FK RESTRICT).
БД также запрещает пересечения интервалов пользователя, два активных интервала,
неположительную длительность и сочетание is_completed=true с is_paused=true.

## Задачи

Все маршруты требуют Bearer-токен. Создание — только в своём проекте.

| Метод | Путь | Тело / результат |
|---|---|---|
| POST | /projects/{project_id}/tasks | {"title":"Задача"} → 201 |
| GET | /projects/{project_id}/tasks | Массив задач → 200 |
| GET | /tasks/{id} | Задача → 200 |
| PATCH | /tasks/{id} | title и/или is_completed → 200 |
| DELETE | /tasks/{id} | Пустой ответ → 204 |

Задача содержит id, project_id, title, is_completed, is_paused и created_at.
Название — 1–200 символов после удаления пробелов по краям.
PATCH не принимает project_id, user_id или is_paused. is_paused меняют только
операции таймера. Завершённые задачи остаются в списке; повторное открытие
через is_completed=false разрешено. Перед is_completed=true требуется остановить
активный/приостановленный таймер. Чужие проекты/задачи возвращают 404.

Коллекция Postman дополнена запросами задач; сначала удаляйте задачу, затем проект.

## Таймер, история и отчёты

[Эндпоинты и правила таймера, интервалов, отчётов](docs/BACKEND_2_API.md).
Пауза закрывает интервал, продолжение открывает новый. tasks.is_paused отражает
состояние задачи; паузы не входят в рабочее время. Остановка таймера и завершение
задачи — разные действия.

## Пересоздание БД

По запросу БД пересоздана с новым томом. Прежние регистрации и проекты удалены,
нужно зарегистрироваться заново. Для следующих изменений схемы сброс тома
не обязателен: можно выполнить согласованный ALTER TABLE с сохранением данных.

## Как устроен код

Controllers разбирают HTTP и вызывают сервисы. AuthService валидирует данные,
хеширует пароли и работает с JWT; ProjectService проверяет поля проектов.
Repositories содержат параметризованный SQL. Проверка JWT общая для всех
защищённых маршрутов и дополнительно проверяет наличие пользователя в БД.
Два рабочих потока Trantor выполняют хеширование и синхронные SQL-запросы,
не блокируя сетевые потоки Drogon. Это простой вариант для локального MVP.

C++-модели — структуры, а не SQLAlchemy-модели: ограничения задаёт init.sql.
std::optional соответствует возможному NULL, std::chrono — моменту времени.
std::shared_ptr позволяет обработчикам владеть общим сервисом; лямбды с захватами
сохраняют необходимые данные, пока запрос выполняется в рабочем потоке.

## Проверка таймера в Postman

После Login, Create project и Create task откройте папку
**Timer, history and reports** в коллекции Postman. Все запросы используют сохранённые
access_token и task_id. Выполняйте Start → Active → Pause → Resume → Stop.
Для каждой операции POST передаётся `{"task_id":"UUID"}`.

- Start и Resume возвращают 201 и новый интервал.
- Pause возвращает 200 и закрытый интервал; задача получает is_paused=true.
- Stop возвращает 200, task и time_entry (null, если остановили задачу на паузе).
- Active возвращает интервал или JSON null.
- Повторный Start при работающем таймере — 409; Stop не завершает задачу.

Таймер хранится в БД: можно перезапустить сервер, затем вызвать Active/Stop.
Сервер не считает секунды в цикле; клиент отображает разницу текущего времени
и started_at, а сервер вычисляет длительность для отчётов.

История: `GET /time-entries?task_id=UUID&limit=100&offset=0`.
Создание ручной записи:

```json
{
  "task_id":"UUID",
  "started_at":"2026-01-01T10:00:00+03:00",
  "ended_at":"2026-01-01T11:00:00+03:00"
}
```

PATCH /time-entries/{id} принимает started_at и/или ended_at; DELETE удаляет
закрытую запись. Пересечения запрещены по пользователю, включая разные задачи.
Оба времени ручной записи должны быть в прошлом; формат обязательно с часовым поясом.
Активный интервал редактировать/удалять нельзя: сначала Stop.

Отчёт: `GET /reports?from=2026-11-01&to=2026-11-10&group_by=day`.
Даты включительно, календарный часовой пояс Europe/Moscow. Допустимы
group_by=project/task/day и фильтры project_id/task_id. Период обрезает интервалы;
работающий таймер учитывается до as_of, указанного в ответе.

В коллекции ручной интервал создаётся за два дня до текущего времени, а отчёт
строится за последние семь дней. После теста таймера его интервалы остаются:
DELETE задачи/проекта вернёт 409, пока история не удалена. Это защита данных.

При запуске через Docker после изменений кода выполните `docker compose up --build -d --wait`.
Для локального запуска пересоберите `cmake --build build --parallel 2` и перезапустите сервер. Схема БД не менялась,
пересоздавать Docker-том не нужно.
