# Контракт для второго бэкендера: таймер, интервалы, отчёты

Все перечисленные маршруты реализованы в TimerController/Service,
TimeEntryRepository, ReportController/Service и ReportRepository.
Этот документ описывает фактический контракт API.
CRUD задач и проектов уже реализован; их маршруты дублировать не нужно.
Общую схему database/init.sql менять только после согласования с владельцем схемы.

## Общие правила

- Все маршруты защищены `Authorization: Bearer <access_token>`.
- JWT HS256, срок 1 час. Использовать существующий `AuthService::authenticate`.
- user_id берётся из авторизации, не из JSON или query. Каждый запрос ограничен владельцем.
- Принадлежность задачи проверять через tasks → projects.user_id; совпадение time_entries.user_id
  с владельцем задачи проверяет сервис. Сам FK на user_id не гарантирует это совпадение.
- UUID — строки; время — ISO 8601 с обязательным Z/смещением. Вывод UTC с Z.
- Ошибка: `{"error":"..."}`. 400 — неверные поля/диапазон; 401 — авторизация;
  404 — отсутствующий/чужой объект; 409 — конфликт состояния/пересечение интервалов;
  500 — внутренняя ошибка без SQL и секретов в ответе.
- Не блокировать сетевой event loop: использовать общий рабочий пул или асинхронные запросы.
- Для каждой операции таймера — транзакция: сначала заблокировать пользователя
  `SELECT id FROM users WHERE id=$1 FOR UPDATE`, затем затронутую задачу `FOR UPDATE`.
  Это сериализует запуск/паузу/остановку и ручное изменение интервалов в нескольких окнах клиента.
  CRUD задачи также блокирует задачу перед изменением/удалением.
- После блокировок повторно проверить владельца, выполненность и состояние таймера.
- В текущей версии Drogon ошибки PostgreSQL могут быть общим orm::Failure, а не
  UniqueViolation/ForeignKeyViolation. Не рассчитывать только на конкретный подкласс:
  проверять ожидаемые конфликты в транзакции, сохранять ограничения БД как последнюю защиту.

## Данные и состояния

Четыре таблицы уже созданы: users, projects, tasks, time_entries.

`tasks`: id, project_id, title, is_completed bool, **is_paused bool DEFAULT false**, created_at.
`time_entries`: id, user_id, task_id, started_at, ended_at nullable.
На задачу разрешено несколько рабочих интервалов. Отдельной таблицы пауз нет.

| Состояние задачи | is_completed | is_paused | Активный интервал |
|---|---|---|---|
| Ещё не запущена / остановлена | false | false | Нет |
| Работает | false | false | Есть |
| Пауза | false | true | Нет |
| Завершена | true | false | Нет |

Пауза закрывает рабочий интервал и ставит tasks.is_paused=true.
Продолжение создаёт новый интервал, tasks.is_paused=false. Время паузы не учитывается.
Stop завершает работу таймера, но НЕ отмечает задачу выполненной.
Выполнение задачи — отдельный PATCH /tasks/{id} с is_completed=true.
CRUD отклоняет завершение задачи, если она на паузе или имеет активный интервал: сначала Stop.
is_paused доступен только для чтения в CRUD; менять его должны операции таймера.
Можно иметь несколько задач на паузе, но только один активный интервал на пользователя.
Завершённую задачу нельзя start/resume; прошлые интервалы сохраняются.
Архивации сейчас нет: projects.is_completed означает завершённость проекта. Дополнительный
запрет таймера для завершённого проекта не вводить без согласования.

БД гарантирует ended_at > started_at, не более одного активного интервала на пользователя
и отсутствие пересечений его интервалов. Интервалы полуоткрытые [start,end): соседние
10:00–10:30 и 10:30–11:00 допустимы. NULL ended_at означает бесконечную верхнюю границу.
При ошибке транзакция откатывается целиком, включая изменение is_paused.

## Эндпоинты таймера

| Метод | Путь | JSON | Успех |
|---|---|---|---|
| POST | /time-entries/start | {"task_id":"UUID"} | 201, новая запись |
| POST | /time-entries/pause | {"task_id":"UUID"} | 200, закрытая запись |
| POST | /time-entries/resume | {"task_id":"UUID"} | 201, новая запись |
| POST | /time-entries/stop | {"task_id":"UUID"} | 200, {"task": task, "time_entry": entry_or_null} |
| GET | /time-entries/active | — | 200, запись или null |

Start: задача не завершена, не на паузе, активного интервала пользователя нет.
started_at=серверное now(), ended_at=NULL. Повторный Start активной задачи — 409.
Pause: активный интервал принадлежит указанной задаче; ended_at=now(), is_paused=true.
Повторная Pause без активного интервала — 409.
Resume: только задача на паузе; нет активного интервала пользователя; создаётся новая запись.
Stop работающего таймера закрывает интервал и оставляет is_paused=false.
Stop задачи на паузе только сбрасывает is_paused; возвращает time_entry=null, без нового интервала.
Stop задачи, которая уже остановлена, — 409. Чужой активный таймер не затрагивать.
Для Pause/Stop обеспечить положительную длительность; мгновенная остановка не должна
нарушать ended_at > started_at (при нулевой длительности вернуть 409 и оставить состояние).

Запись времени в JSON:

```json
{
  "id":"UUID",
  "user_id":"UUID",
  "task_id":"UUID",
  "started_at":"2026-11-09T07:00:00Z",
  "ended_at":null
}
```

## История и ручные записи

| Метод | Путь | JSON / query | Успех |
|---|---|---|---|
| GET | /time-entries | from, to, project_id, task_id, limit, offset | 200, массив записей |
| POST | /time-entries | task_id, started_at, ended_at | 201, запись |
| PATCH | /time-entries/{id} | started_at и/или ended_at | 200, запись |
| DELETE | /time-entries/{id} | — | 204 |

from/to — необязательные timestamp-фильтры; проверять from < to при наличии обоих.
По периоду выбирать пересекающиеся интервалы: started_at < to AND
(ended_at IS NULL OR ended_at > from). Сортировка started_at DESC, id DESC.
limit: по умолчанию 100, диапазон 1–500; offset: по умолчанию 0, неотрицательный.
Если фильтры project_id/task_id заданы, проверить принадлежность; несовместимая пара — 400.

Ручное создание допускает только закрытый интервал с ended_at > started_at и временем
не позднее now(). Новую запись для завершённой задачи не создавать. Редактирование
и удаление прошлых закрытых интервалов завершённой задачи разрешено, чтобы исправить историю.
PATCH не меняет task_id/user_id; оба времени после изменения должны оставаться заполненными.
Активный интервал вручную PATCH/DELETE не менять — 409; сначала Stop.
Проверять пересечения по пользователю, а не только по задаче; при PATCH исключать текущий id.
Редактирование истории не меняет tasks.is_paused и не запускает таймер.

## Отчёты

| Метод | Путь | Query | Успех |
|---|---|---|---|
| GET | /reports | from, to, group_by, project_id?, task_id? | 200, JSON |

Предлагаемый формат: обязательные from/to — даты YYYY-MM-DD, обе включительно;
group_by=project\|task\|day, по умолчанию project.
Календарный часовой пояс Europe/Moscow. Внутренний период:
[from 00:00, день после to 00:00). Проверять from <= to.

Длительность обрезать границами выбранного периода. Активный интервал считать
до единого as_of=now() на весь отчёт; в JSON возвращать as_of. Для group_by=day
интервал, пересекающий полночь, разбивать по дням. Паузы в сумму не попадают.
Суммировать точную длительность и округлять до целых секунд после суммирования.

```json
{
  "from":"2026-11-01",
  "to":"2026-11-09",
  "timezone":"Europe/Moscow",
  "group_by":"project",
  "as_of":"2026-11-09T12:00:00Z",
  "total_seconds":3600,
  "items":[{"project_id":"UUID","project_name":"Проект","duration_seconds":3600}]
}
```

Для task: item содержит task_id, task_title, project_id, duration_seconds.
Для day: date, duration_seconds. При отсутствии записей items=[], total_seconds=0.
## Что обязательно проверить

Вход чужого пользователя, завершённые задачи, Start/Start одновременно,
Pause/Resume/Stop, Stop на паузе, отсутствие учёта пауз, несколько задач на паузе,
ручные пересечения и соседние интервалы, редактирование без пересечения с самим собой,
отчёты на границе периода и московской полуночи.
Состояния задачи и интервалы должны сохраняться/откатываться в одной транзакции.

## Проверка и реализация

Все операции изменения интервалов сериализуются по users.id; Start/Resume/Pause/Stop
также блокируют задачу. HTTP-успех отправляется только после подтверждения COMMIT.
Время таймера берётся из PostgreSQL clock_timestamp() после ожидания блокировок.
Таймер сохраняется в БД и продолжает работу после перезапуска бэкенда.
Отдельного фонового потока, который увеличивает счётчик каждую секунду, нет:
длительность вычисляется из started_at и ended_at/as_of.

Для истории timestamp допускает дробную часть 1–6 знаков и смещение до ±14:00.
В отчёте total_seconds округляется после суммирования точных длительностей;
каждая группа округляется отдельно. Поэтому при долях секунды сумма округлённых
групп может отличаться от total_seconds на секунду. 

Команда `docker compose run --rm --build tests` (или `python3 tests/integration.py`
при локальной сборке) проверяет весь API в отдельной временной БД,
включая перезапуск сервера, параллельный Start, паузы, пересечения, отчёты.
